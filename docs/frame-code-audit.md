# Frame Code Audit: Summit Adventure Series `SHAPE-FEATURES` → `SHAPE-FEATURES-LENGTHxWIDTH`

Phase 1 of `Frame_Code_Implementation_Prompt_1.md`. This audit is **read-only**: no code, monday.com, database or integration was changed.
Branch: `claude/frame-code-dimensions` (CLAUDE.md requires the `claude/` prefix in place of `feature/`). Audited 2026-10-21 against `main` @ `1d2e5e4`+.

Database figures come from SELECT-only queries against the `.env` database (Neon, which appears to be production). monday.com figures come from read-only board, item and automation reads.

---

## 1. Summary

1. **There is one generator, and nothing parses the code to price anything.** The code is built only in `frameModelNumber()` (`src/proposals/adventureSeries.ts:167`). It goes into a single place, the first GROUP heading `"<CODE> — Itemized"` (`:541`), which is saved into `ProposalVersion.items`.
   - No pricing, BOM, hardware, freight, rules, handoff or reporting code parses the frame code. They all read SKUs or the structured `meta.advAnswers`. **No pricing or BOM flag to raise.**
2. **The browser reads the code back out of the heading text.** It does this in five places in `public/` (§3). Three of them break or misbehave with the new format:
   - the **title-model warning and its "Use model" button** (false warnings; the button appends the dimensions again on every click);
   - the **PDF filename** (`…-10x10-10x10-…`);
   - the **CSS uppercase** on the proposal heading and QBO's `.toUpperCase()` (`10X10`).
3. **The dimensions already come from the right place.** The configurator's `adv.length` / `adv.width` (Frame Dimensions dropdowns) become `advAnswers.length` / `width`. That feeds the engine, the heading note and the monday Length/Width columns. No mat SKU or label supplies them. **There is no width ≤ length check today** (length 6–30, width 6–20). In the 104 saved configurations, none has width > length.
4. **monday.com needs no structural change.**
   - No board formula, automation or server code parses the model code.
   - Deal Tracking column `text29__1` is titled **"Model"**, but the app writes the **proposal title** into it.
   - Length and width are written as numbers from `advAnswers`.
   - The only routes for the new code into monday are the title, which the rep controls, and the uploaded PDF's file name.
5. **There is no PandaDoc, Shopify or Zapier code in this repository.** The integrations that exist are QBO, DocuSeal and monday.
6. **There is no database column for the code or the dimensions.**
   - The code lives in `ProposalVersion.items` (JSON heading).
   - The answers live in `ProposalVersion.sections[id=meta].data.advAnswers`.
   - Frozen copies live in `AcceptedOrder.contentSnapshot`, which is integrity-hashed.

## 2. The generator, and how it compares with the spec

`src/proposals/adventureSeries.ts:167-186`:

```ts
shape = Square→SQ | L-Shape→L | T-Shape→T | else R
beams = (interiorBeams ? interiorBeamsQty : 0) + (monkeyBars ? 1 : 0)   // MB occupies its own bay
code  = [beams>0 ? beams] + [MB] + [L<ladders>] + [T if trolley && type==Dual] + [Z] + [R]
return `${shape}-${code}`                                                // "SQ-" when nothing selected
```

| Spec rule                                       | Today                                                                                                                                       | Gap                                          |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| `SHAPE-FEATURES-LxW`, lowercase `x`             | No dimension segment                                                                                                                        | Add it                                       |
| No features → `SQ-10x10`, never a double hyphen | Returns `SQ-` (dangling hyphen)                                                                                                             | Fix                                          |
| Feature order beams, MB, L#, T, Z, R            | Same order                                                                                                                                  | —                                            |
| T = dual trolley                                | T only when `trolleyType === 'Dual'`                                                                                                        | Matches                                      |
| Ladder always `L1`/`L2`                         | Emits `L<n>`. The configurator allows **up to 4** ladders (`min(4, legs)`, app.js:9761). **3 saved configurations have 3 or more ladders.** | **Decision D1**                              |
| Beam count 1–6                                  | Interior beams 1–6, plus 1 when MB is on, so the digit can reach **7** (no saved configuration does)                                        | **Decision D2** (beam logic must not change) |
| Length ≥ width, validation error                | No check anywhere                                                                                                                           | Add (UI and server)                          |
| Shape from Configuration, not inferred          | `config` comes from the auto rule (L = W → Square, else Rectangle) or a manual override for L/T. 6 saved L/T configurations.                | Matches                                      |
| Feature table data-driven                       | Hard-coded in the function                                                                                                                  | Move to a data file (**D4**)                 |

**How the spec's test cases read against the beam rule.** "2 beams, MB → `2MB`" only holds if "2 beams" means the **digit**: 1 interior beam plus the MB bay. With 2 interior beams ticked and MB on, today's (unchangeable) logic gives `3MB`. I will write the tests against the digit (§1 inputs as written, read as code digits) unless told otherwise. See **D2**.

## 8. Proposed design for Phases 2–3 (for your approval)

- **`src/proposals/frameCode.ts`** + **`src/proposals/frame-code-features.json`** (feature table: key, letter, order, which answer drives it, count suffix).
  - Exports `buildFrameCode`, `parseFrameCode`, `normalizeFrameCode`, `isValidFrameCode`.
  - Scoped by product line, with Adventure the only template.
  - Beam digit and trolley rules reuse today's logic **unchanged**.
- **The server is the only generator.** The `/adventure-series/price` route stamps `frameCode`, `frameLength` and `frameWidth` onto the itemized heading line, alongside the heading text.
  - The browser **reads** those stamped fields and stops parsing text.
  - For legacy lines, the browser falls back to the heading text. Old code plus stored dimensions is upgraded through a small `normalize` in a single shared browser helper (`public/frame-code.js`), kept in lockstep with the TS module by a unit test that runs both against the same cases. (The browser is unbundled vanilla JS and cannot import the TS module.)
- **Width ≤ length** is enforced in three places:
  - the configurator (width options filtered, plus an inline message);
  - the server (`/price` returns 400, no code generated);
  - proposal save, blocked while invalid.
- Fix §3 #9, #11/12, #18, #21, #22, #23 and #25. Keep the Frame Dimensions note (#19/#24).
- Writing the code back into old headings: none. Old versions display their stored heading. Filename, title check and e-sign use the normalized code when dimensions are available.
